# Spy numbers at Tracks' volume, 28 Sep 2026

`numbers/volume_test.go` on made-up data shaped like Tracks' on 27 Sep
(tracks/measure/hourclose-direction): 29,274 ads, 12,000 creatives, 2,000
accounts, 293 operators, 25 verticals, 28 publishers on 2 devices, 53,369
ad_hourly rows in the last hour, 96 hours of hourly counts (the last 24
hours and the same hours 1 to 3 weeks back) and 22 days of daily counts
(2.4 million rows). Run in a cloud container (4 vCPU, Postgres 16,
default settings); a CX43 has 8.

```
SPY_VOLUME=1 PG_TEST_URL=... go test -run TestVolume -v -timeout 60m ./numbers/
```

| Step | Runs | Took |
|---|---|---:|
| Read model, first run (fills every creative's days) | once | 7.7 s |
| Read model | every 5 minutes | 6.6 s |
| Direction rebuild (members, usual publishers, noise) | once a day | 190 s |
| Direction usual value, the collector's query, one slot hour | | 3.7 s |
| Direction usual value, new query, one slot hour | hourly | 3.2 s |
| Direction first run of the day (rebuild and 8 slot hours) | once a day | 220 s |
| Direction | every 5 minutes | 5.4 s |
| Last 24 hours, creatives and operators | when Tracks closes an hour | 21 s |
| Last 24 hours, nothing new closed | every minute | 3 ms |
| Creative range, 24 hours | when asked | 15 s |

| Operator range, 7 days | when asked | 2.6 s |
| Vertical range, 7 days | when asked | 2.3 s |
| Publisher range, 7 days | when asked | 0.8 s |

Measured before the one-publisher fading guard, which adds one pass over
the strata to each range.

## What it says

- Everything that runs on a schedule fits: the 5-minute work (read model
  and Direction) takes about 12 s, and the hourly work (the last 24 hours
  and one slot hour) about 25 s.
- The collector's usual value query was **not** slow on this data (3.7 s
  against the new one's 3.2 s). On prodbox it took about 4 minutes a slot
  hour because the planner joined its CTEs with nested loops on real
  distributions. The new query goes through analysed temporary tables, so
  it cannot pick that plan, but only a run on real data proves the
  4 minutes are gone.
- Two slow runs found and fixed on the way: the read model's first run
  took over 6 minutes (the lifespan days were filtered against the table
  being filled), and the 24-hour creative range took 46 s (a slot worked
  out per row by date functions, text keys, checks summed per subject).
- A creative list over a custom range takes 10 to 15 s: it reads every
  hourly row of the range and its usual weeks (2.6 million for 24 hours)
  and keeps a million publisher, device and hour cells. That is too slow
  for a page's 5-second timeout. The app should run ranges with a longer
  timeout behind a loading state and keep each answer (a range only
  changes when Tracks closes an hour again); the last 24 hours are
  stored and open at once.
- Direction's daily rebuild takes 3 minutes and holds up that one 5-minute
  tick. Worth splitting into its own job if it grows.
